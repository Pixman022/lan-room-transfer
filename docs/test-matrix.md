# POC field test matrix

Status (2026-11-18; updated 2026-11-19): **User reports successful bidirectional file transfer between real devices after restricted P2P mode was deployed.** This confirms the basic send/receive path was exercised by the user, beyond the previous room-entry-only result. File sizes, saved-file SHA-256 comparisons, repeated-run reliability, device/browser versions, and cross-network security have **not** been independently verified. Earlier "未通过/未测试" responses were ambiguous and are superseded only for the basic transfer scenario.

**Connection stability follow-up (2026-11-18):** User reported that establishing a peer connection sometimes takes unusually long and behaves inconsistently. This is an observation, not yet a measured failure rate. Code fixes now serialize incoming SDP/ICE operations, send local SDP before buffered candidates, forward ICE end-of-candidates, and show an explicit status after 12 seconds while permitting late recovery. Do not equate this to verified performance improvement until separate devices repeat the test. For each retry, record `stage`, `elapsedSeconds`, `candidatesSent`, `candidatesReceived`, `ice`, `channel`, and `reason` from the privacy-reduced diagnostics on both devices. Browser automation here could only test mocked peer sequencing, not a genuine routed LAN path.

**Follow-up after user diagnostics (2026-11-18):** An actual client reported `signalErrors=1` with `目标设备已离线`, while a peer remained at `answer-sent / ice:new`. The root cause candidates were live-session refresh creating duplicate member IDs and stale signals recreating peers after a disconnect. The fix assigns each WebSocket incarnation a generation, uses authenticated session takeover, and prevents stale ICE/SDP/offline messages from mutating the new peer. The latest Python server integration tests passed. **Repeated field reliability is still untested**; test 10 quick refresh/rejoin cycles with two real devices before closing this item. After a new deployment both open pages must be refreshed because signaling payloads now include generation IDs.

**First-join ordering fix (2026-11-18):** A user reproducibly observed that PC entering a phone-created room only worked after exiting and rejoining. The server previously sent `welcome` to the PC before `peer-online` to the already-present phone, allowing the PC's initial WebRTC offer to arrive before the phone created its peer object; the browser ignored such an unknown offer. The server now announces the peer to existing members **before** welcoming the newcomer, so ordered WebSocket delivery on the existing member protects initial offer processing. Server integration coverage verifies notification ordering even when the newcomer sends its offer immediately. **Field confirmation remains pending**; if the fault persists, compare both browsers' `?debug=1` logs rather than assuming the race was the only cause.

**ICE-only stall update (2026-11-18):** After a successful signalling recovery, a user again observed `signal=connected`, `signalErrors=0`, `connection=new`, `ice=new`, `channel=none`, `stage=answer-sent` for 46 seconds. The old 12-second timer only updated the message and did not renegotiate. The new bounded protocol carries an ICE `attempt` with SDP and candidates, permits responder `retry` requests, re-creates the peer connection up to three attempts and ignores prior-attempt messages. The browser diagnostics now include `attempt`, `signalingState`, `iceGathering` and whether local/remote descriptions were set. This is **not** yet validated on a physical LAN. Both sides must reload after deployment because the ICE signalling protocol changed.

## Five-run device acceptance for the 2+2 ICE strategy (baseline, 2026-11-19)

**User-reported five-run results:** Windows PC Chrome created a room, mobile Firefox joined with one click. Four of five rounds automatically reached P2P-ready (80% observed, only five trials). The successful runs were: attempt 4 / 15 s / file saved; attempt 3 / 35 s / file saved; attempt 4 / 15 s / file saved; attempt 3 / 34 s / file outcome unconfirmed. Round five failed or needed manual reconnection, with no diagnostic snapshot supplied. Of the four successful connections, the mean reported first-ready duration was **24.75 s** (median **24.5 s**, range **15–35 s**). Three confirmed successful file receipts, one unconfirmed; saved-file SHA-256 compared against the source remains unverified. All successful rounds required the reverse-offerer phase. The attempt-3 runs were slower than attempt-4 runs in this small sample; **do not infer a causal relationship** without per-attempt timing/ICE-state evidence.

**Deferred follow-up — [issue #6](https://github.com/Pixman022/lan-room-transfer/issues/6):** The user elected on 2026-11-19 to postpone further ICE reliability tuning. When resumed, test PC Chrome creates room → mobile Firefox joins with **one click**, without manually leaving or reloading. Repeat five new independent sessions after this diagnostic patch. For each, record: whether automatic P2P-ready was reached, final `attempt`, `setupElapsedSeconds` or `timeToReadySeconds`, whether manual intervention was needed, whether a small file was saved successfully, and any failure diagnostic from both peers. A successful automatic third attempt is **not** a first-attempt success. The browser-only metric starts at peer creation, not the UI Enter Room click. Do not publish full-debug reports (they contain secrets and addresses); ordinary redacted JSON is sufficient. The 2+2 strategy remains provisional until field data exists for more than one join.

To collect follow-up evidence, open **诊断** next to the online device count and use **复制诊断** separately on each device. The ordinary copied report excludes room code, member names, file names, and network IP addresses; it now includes `peers[].iceDiagnosis` counts/interpretation and falls back to a local redacted JSON download if mobile clipboard access is blocked. Record whether the status says 房间已连接, 直连未就绪 or 文件直连就绪; also record whether the uploader's file shows 等待设备直连 or 可供 N 台设备接收. Do not infer that "房间已连接" means the file path is ready. The approved restricted P2P policy includes a narrow verified host/prflx exception; it is not a physical LAN guarantee.
